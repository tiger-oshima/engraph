# Vision — Engraphの目指すもの

## 中心思想

> 開発とは、要求に基づいて成果物の構造・性質と振る舞いを段階的に決定し、その実現を確かめていく活動である。

「営業管理を楽にしたい」も「保存ボタンを青色にしたい」も「Three.jsを使用する」も、抽象度や提起者が異なるだけで、すべてRequirementとして扱う。

要求の登録時に対象Artifactが存在するとは限らない。まず要求を受け取り、開発者がトリアージし、必要に応じて要求を導出し、Artifactの構造や性質を具体化する。開発が進んだ後には、既存の画面やボタンを直接対象とする要求も受け付ける。

## 解決したい問題

- なぜその成果物が存在するのかを、要求までさかのぼって説明しづらい。
- ある要求がどの成果物に反映されているかを横断的に把握しづらい。
- 変更によって影響しうる要求・成果物の経路が見えにくい。
- 要求の導出が妥当か、実現が検証済みかを区別して追跡しづらい。

## 提供価値

**要求から成果物までの接続性を、3D空間で直感的に把握できること。**

Artifactの包含階層とRequirementの導出関係は異なるグラフであり、Realizationが両者を接続する。利用者は全体を俯瞰しつつ、任意のArtifactやRequirementを選択して関連経路を追跡できる。

目指す問いは次のとおり。

1. このArtifactは、何の要求を実現するために存在するのか。
2. このRequirementは、どのArtifactに対応しているのか。
3. このArtifactを変更すると、どの要求・成果物に影響する可能性があるのか。
4. どの導出・実現がまだ評価されていないのか。

## Coreの設計原則

- **高い抽象度を保つ。** System、Database、AppServerなどのサブタイプをCoreに固定しない。
- **要求を一元化する。** 動機、目的、制約、技術選定もRequirement。PropertyやRationaleを別エンティティにしない。
- **対象未定の要求を許す。** RequirementとArtifactの対応は後から決められる。
- **構造と導出を分ける。** Artifactの包含とRequirementの導出は独立した関係。
- **実現と評価を分ける。** Realizationの登録だけで充足済みとは判定しない。
- **工程を固定しない。** ウォーターフォール、アジャイル、スパイラル等のプロセスをCoreに埋め込まない。
- **複雑さを必要以上に増やさない。** 汎用Node、汎用Relationship、不要な中間概念を導入しない。

## スコープ

Engraphは要求・成果物のモデリング、トレーサビリティ、可視化、実装作業への橋渡しを目指す。コードの実装そのものをEngraph Coreの責務にはしない。

現段階ではコンセプトとデータモデルの合意を優先し、フレームワーク、永続化方式、拡張方式など未決定の技術を確定事項として記載しない。
