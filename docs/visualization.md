# 3D Visualization — UIの方向性

## 中心体験

Artifactの包含階層とRequirementの導出関係、そして両者を結ぶRealizationを**一つの3D空間**で俯瞰する。全体の接続性を把握できることを優先する。2Dマインドマップへの置き換えはしない。

## 視覚表現（決定事項）

| 対象 | 表現 |
| --- | --- |
| Artifact | **黄色い立方体** |
| Requirement | **青い球体** |
| Artifactの包含関係 | 立方体同士の接続線 |
| Derivation | 球体同士の接続線 |
| Realization | 球体と立方体を結ぶ接続線 |
| 3D描画技術 | **Three.js** |

色や形は単なる装飾ではなく、ノードの種類を直感的に判別するための意味を持つ。

## 基本操作（構想）

1. 空間を回転・パン・ズームして、全体を探索する。
2. Artifactを選択すると、その祖先・子孫の包含経路を強調する。
3. 選択ArtifactのRealizationをたどり、対応するRequirementとその導出経路を強調する。
4. Requirementを選択すると、導出関係とRealizationをたどり、関係するArtifactを強調する。
5. 関連しないノード・エッジは目立たなくし、選択した接続経路を把握しやすくする。

**ハイライトするのはノードだけではなく、そこへ至るエッジと経路そのもの。**

## 配置方針（未確定）

ArtifactとRequirementは異なる構造を持つため、同じツリーに押し込まない。3D空間の距離・方向・まとまりに意味を持たせる配置を検討する。ただし「Requirementは必ず上、Artifactは必ず下」などの固定ルールは、使いやすさを検証するまでは決定しない。

ノードの大きさを重要度に対応させる案や、Eventの形状・表示方法も未確定。

## 検証したいUX

- 大規模なグラフでも全体像と局所経路を両立できるか。
- 選択したArtifactが「なぜ存在するのか」を要求まで追跡できるか。
- 未割り当てRequirement、未評価のDerivation/Realizationが見つけやすいか。
- 接続経路が多い場合でも、ハイライトが情報過多にならないか。

UIはデータモデルを変更せず、同じRequirement・Derivation・Artifact・Realizationから構築する。
